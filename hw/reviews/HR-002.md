# HR-002: Review of DR-002, converted asset file format (4-byte header)

- **Verdict: fits**
- Reviewer: microcontroller expert, 2026-10-03. Numbers from `hwtest/flash_read.py`, `hwtest/board_info.py`.

## Numbers
- A 4-byte header costs one extra `readinto` of 4 bytes per load: well under 0.1 ms, against ~1 ms for a 4,480-byte card and ~21–26 ms for a full background.
- Checking length = 4 + w*h*2 needs `os.stat(path)[6]`, which is a filesystem lookup of a fraction of a millisecond. Cheap enough to do on every load.
- Flash: 60 files x 4 bytes = 240 bytes. Irrelevant. The whole asset plan is 0.62 MB in a 1.39 MB free filesystem (HR-F01 explains why only 1.4 MB today).

## What the dev must stay inside
1. Read the header into a preallocated 4-byte `bytearray`, not with `f.read(4)` (which allocates). Then `readinto` the pixel bytes directly into the scratch or framebuffer. No per-pixel Python.
2. Reject a bad file **before** reading pixels, from the stat length, so a bad file never half-overwrites the framebuffer.
3. Byte order of the pixel data is DR-003's question; this format is independent of it.
