# HR-024: Review of DR-024, sprite sheets (one file per image family)

- **Verdict: fits.** Option A, all families. The measured gain is larger than the dev's estimate for the reels and about as estimated for cards.
- Reviewer: microcontroller expert, 2026-10-04. Script `hwtest/sheet_bench.py`: temporary sheets written to `/assets` (8 x 56x56 symbols, 50,180 bytes; 53 x 40x56 cards, 237,444 bytes) and one single-card file, real `lib/lcd.py`, `lib/art.py`, `framebuf`, 62.5 MHz SPI; temps removed afterwards.

## Measured
| Path | Time |
|---|---|
| Open the 237 KB card sheet, once per scene | 3.2 ms |
| **One card from the open sheet**: `seek` + `readinto` 4,480 B **0.9 ms** + keyed blit 40x56 **2.0 ms** | **2.9 ms** |
| One card from its own file, today's `art.py` (open per blit) | 11.4 ms first call, **6.6 ms cached** |
| Code-drawn card (for comparison) | 3.9 ms |
| **Reel: 8 rows (896 B) from the open symbol sheet, `seek` + `readinto`** | **0.26 ms** (max 0.38) |
| Reel today: open + close of a symbol file at each symbol change | 3.7 ms |

Note the per-file card has gone from 5.6 ms (HR-F03, with 1 file in `/assets`) to 6.6 ms with 4 files in the folder. The open cost scales with directory size, as HR-F03 said it would; with John's 60 files it gets worse.

## Reading
- **Cards:** a blackjack result scene with eight cards is 8 x 2.9 = 23 ms of blits from a sheet, against 31 ms code-drawn and 53 ms per-file. The art becomes a speed-up instead of a slow-down, which is the whole point of DR-024.
- **The keyed blit, not the read, is now the cost** (2.0 ms of the 2.9). A card has no transparent pixels except its corners; blitting without the key would be ~1 ms (HR-F03 measured 0.8 ms unkeyed for a 56x56). The dev could blit cards unkeyed and draw the four corner pixels over, or accept 2.9 ms. Not a limit, a note.
- **Reels:** 0.26 ms per frame per reel with no opens at all. Today's build opens a file every symbol change (3.7 ms, once every 7 frames per reel); with the sheet that disappears, so the spin's worst frame equals its steady frame. This alone justifies the symbols sheet.
- **RAM:** one open file per sheet in use, about 100 bytes each; no new buffers. **Flash:** same bytes, fewer headers.
- **Writing a 237 KB sheet to the board took 4.2 s** on the bench; the Viper upload will be similar. John's "one upload instead of 53" holds.

## Limits for the dev
1. Open the sheets on scene entry and close them on exit, as proposed. Keep the file objects out of the frame loop; `seek` + `readinto` only.
2. The reels' per-frame read is 896 bytes: keep reading only the rows that scroll in, not a whole symbol.
3. Validate the sheet's length once at open (DR-002 rule), then trust indices.
4. The jackpot banner stays a single file as proposed; `background` images stay single files.

## Not measured
A sheet with magenta placeholders for missing members (same bytes, same cost). The converter.
