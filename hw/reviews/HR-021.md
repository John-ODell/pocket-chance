# HR-021: Review of DR-021, slots win presentation and one save per spin

- **Verdict: fits**
- Reviewer: microcontroller expert, 2026-10-04. Blink measured with `hwtest/slots_spin_bench.py` on the board (real `lib/lcd.py`, firmware v1.29.0, SPI 62.5 MHz). Save figures from `hw/BUDGET.md` (`pocket_bench.py`, `split_play_bench.py`).

## Blink
| Item | Measured |
|---|---|
| One blink toggle: gold frame on or off around all three 60x60 windows, three `show_rect` pushes | **57.8 ms mean, 85 ms max** |
| Three blinks (6 toggles) | ~0.35 s of drawing, spread over the blink timing |

The dev estimated ~5 ms per window; it is ~19 ms, because `LCD.show_rect` copies the window's rows out of the framebuffer in a Python loop before pushing (60 rows here), and the push itself is only ~1.5 ms. For a blink that runs three times it does not matter. If the frames are to blink faster than ~8 Hz, push the three windows as one 240x60 band with `show_band` (one copy-free push of 28,800 bytes ≈ 4.6 ms + drawing) instead of three `show_rect` calls.

## One save per spin
| Item | Figure | Source |
|---|---|---|
| Save time (tmp, `.bak`, rename) | 54–77 ms mean, **102–151 ms max** | measured, `BUDGET.md` |
| Spin rate, every spin a press of A, ~2 s animation + result | one spin every 3–4 s at the fastest a human will play | DR-020 timing |
| Writes per hour of continuous play | ~900–1,200 | arithmetic |
| Flash endurance | ~100,000 erase cycles per 4 KB block (class figure), 3,840 blocks, LittleFS moves writes across free blocks | datasheet-class estimate |
| Time to wear out at 1,200 saves/hour, even if every save cost one full block erase with no spreading | 100,000 / 1,200 ≈ 83 hours per block, x 3,840 blocks of spreading ≈ **320,000 hours** | arithmetic |

So the write rate is not a concern for the life of the device, by a factor of thousands. The cost that is real is time: 54–151 ms after each spin. Placed after the result is drawn (as the dev proposes, the DR-007 rule), the player sees the win first and the save lands inside the pause before the next press. Fine.

## Limits for the dev
1. Save after the result and the blink are drawn, never between reel stops.
2. Do not save while the blink is running or the blink will stutter by up to 150 ms. Order: reels stop, result and win line drawn, save, then blink. The blink then runs with nothing else on the core.
3. "Save only when the balance changed" is not needed for wear; on slots the balance changes on every spin anyway.
4. Auto-spin (option B) would raise the rate to a spin every ~2.5 s, still harmless for the flash; the reason to leave it out is the one the dev gives, not hardware.

## Not measured
The paytable screen (plain text, one `show()`, ~45 ms like any other full redraw). The jackpot banner blit (200x40 from flash, ~3 ms by the measured read rate).
