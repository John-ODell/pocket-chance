# HR-074: Baccarat as built (UPLOAD.md step 1q, main `b102960`, PR 59)

- **Verdict: baccarat fits. The step as a whole fits with one limit, which needs a three-line fix in `pocket.py` before or with the install.** The game itself is fast, flat in memory and leak-free. But the menu keeps every visited game's rules and table modules loaded, so free memory drains as John moves between games. This is already true of today's board (step 1o). Baccarat makes it a fourth game's worth worse.
- Reviewer: microcontroller expert, 2026-10-05. Board benches from the mount only. Nothing installed. John's `/save.json` and `/save.bak` were backed up to `backups/2026-10-05-board-15/` (balance 891), snapshotted and restored by every bench, and checked byte-identical afterwards. Board soft-reset to its step 1o program at the end.

## What the step changes

## The limit: game modules stay loaded after leaving a game
`play()` removes only the game's main module from `sys.modules`. Its `_rules`, `_table` and `_seats` modules stay loaded, and so do `cards` and `poker`. Measured with `hwtest/menu_tour_bench.py`, which runs the staged `pocket.py`'s own `play()` for each game in turn:

| Menu free after visiting | Step 1q as merged | Step 1o (on the board now) | 1q with the fix below |
|---|---|---|---|
| Start | 66,496 | 66,672 | 66,336 |
| Blackjack | 58,976 | 59,168 | 63,744 |
| Ultimate | 45,344 | 45,424 | 56,928 |
| Caribbean | 39,440 | 39,648 | 56,528 |
| Baccarat | 34,784 | | 55,664 |
| Second lap | **MemoryError** entering Blackjack | **MemoryError** entering Ultimate | 55,664 after every game |

Under the harness both builds fail on the second lap: the next game's import cannot find 1,336 contiguous bytes. On a live board there is about 10 KB more headroom, so the failure needs more game changes, but nothing here proves it cannot happen. If it does, `pocket.py` has no error handler, so the program stops with the last screen still showing. To John that looks like a freeze. This is not what happened to John's Caribbean freeze, where the program was alive in its key loop (HR-F06).

**The fix, measured on a bench-only copy and left for the dev to make:** in `play()`'s `finally`, drop every module named after the game:
```python
for m in list(sys.modules):
    if m == modname or m.startswith(modname + '_'):
        del sys.modules[m]
```
With it the menu sits at 55,664 B after any number of visits. Only `cards` and `poker`, which are shared, stay loaded. Every game's sub-modules already carry its prefix (`blackjack_`, `holdem_`, `caribbean_`, `baccarat_`). The safety-net branch (HR-073) would turn the same error into a message and a return to the menu, but does not prevent it. The fix does.

## Notes, not defects
- After a result, a joystick move changes side or stake and the old cards stay on the table until the next deal. That is cosmetic.
- The first version of my timing bench ran itself out of contiguous RAM by keeping every timing in lists. The game was not at fault. It now uses running totals.
