# HR-016: Review of DR-016, split pairs (two hands in the player band)

- **Verdict: fits**
- Reviewer: microcontroller expert, 2026-10-04. Script `hwtest/split_bench.py`, run on the board with the dev's real `lib/` and `games/` code (step 1b build), firmware v1.29.0, SPI 62.5 MHz, code-drawn cards (no art yet).

## What I measured
The dev's proposed layout drawn with the real `Screen` primitives: two hands side by side in the player band, cards at a 20 px step (hand width 100 px), 16 px gap, total and gold marker under the active hand, the other dimmed, then `draw_bottom()` and the same 142-row `show_band` a hit uses today.

| Case | Mean | Max | Today's equivalent |
|---|---|---|---|
| Right after the split, 2 + 2 cards | 38.2 ms | 47.9 ms | single hand, 4 cards: **36.6 ms** |
| 3 + 2 cards | 41.8 ms | 48.5 ms | |
| **Worst case 4 + 4 cards** | **52.6 ms** | 54.9 ms | |
| One code-drawn card (rect + rank + two suit glyphs in scaled text) | 3.9 ms | | |
| RAM for a second hand (4 cards + bet) | **64 bytes** | | |
| Free RAM after the bench, `gc.collect()` | 67,168 | | |

Geometry: hand width 100, gap 16, left edge x=12, right edge x=228. Fits 240 px with 12 px each side.

## Reading
- A split adds **~16 ms to the worst redraw** (8 cards instead of 4), because each code-drawn card is 3.9 ms. That is a redraw at 19 fps instead of 27 fps, once per key press, which no one will notice.
- With card art the picture improves: a 40x56 blit from flash is about 1 ms (`hw/BUDGET.md`, flash read), so 4 + 4 drops to roughly 30 ms, of which ~21 ms is the band on the wire.
- RAM is a non-issue: 64 bytes.
- Nothing else in the band changes: same rows, same push.

## Limits for the dev
1. Keep the split layout inside the existing 142-row band so the dealer, bankroll and prompt areas are not redrawn. The bench confirms it fits.
2. Draw the whole band once per key, as today, not per hand.
3. Rules choice (B vs B3) does not change the hardware cost; aces split like any other pair draw the same number of cards or fewer. Pick on game grounds.

## As built (step 1c, measured 2026-10-04, `hwtest/split_play_bench.py`)
Scripted play of the dev's real split code on the board: **3 natural splits in 18 deals, no errors** (J-J, 7-7, T-T), both hands played, double after split taken 3 times, a rigged A-A got one card each and the round ended at once.

| Path | Mean | Max |
|---|---|---|
| Press Y (split, redraw) | 51.5 ms | 55.6 ms |
| Hit / double on a split hand (band) | 40–42 ms | 43 ms |
| Key → result banner, split round | 99.6 ms | 103 ms (single hand: 82 ms) |
| Stand that ends the round, whole call incl. save | 213 ms | **256 ms** |
| RAM free after the run | 59,568 | |

The 256 ms is the save (LittleFS housekeeping, 110–150 ms here) plus a ~100 ms two-hand result draw. It is at the top of the budget's "up to ~250 ms once per round" allowance and the player sees the banner after ~100 ms, with the save after it, so it is acceptable. If John ever feels a hitch, the fix is the art (cards at ~1 ms instead of 3.9 ms), not the rules.

## Not measured
The result screen with two outcomes and the combined net (text only, same band; estimate +5 ms for two extra size-1 strings). The 4 + 4 layout was left on the panel for John to glance at; a verdict on readability is his, not mine.
