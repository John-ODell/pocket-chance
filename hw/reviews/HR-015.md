# HR-015: Review of DR-015, adopt the peripheral-clock fix

- **Verdict: fits**
- Reviewer: microcontroller expert, 2026-10-04. Numbers from `hwtest/clk_peri.py`, `hwtest/clk_peri_fix.py`, `hwtest/spi_clock.py`, `hwtest/frame_full.py` (all 2026-10-03, firmware v1.29.0), plus John's visual check 2026-10-04 (`hwtest/byteorder.py`).

The dev's description of the fix matches what I ran: same register, same three writes, same datasheet section. The sketch in the DR's appendix is the sequence from `hwtest/clk_peri_fix.py` with an idempotency check added, which is an improvement.

## The panel at 62.5 MHz
John's visual check on 2026-10-04 (`byteorder.py`) ran on the shipped clock, so it confirms the panel at 24 MHz, not at 62.5 MHz. The 62.5 MHz runs that produced correct timing were `frame_full.py` on v1.22.2 (hundreds of frames, four solid colours cycling) and `clk_peri_fix.py` on v1.29.0 (50 frames), but nobody *looked* at the panel during either. The old program drove it at 62.5 MHz for years on the original Pico, so I expect no problem, but the first upload with the fix should include a one-glance check that the menu looks right. I will do that check from the terminal the next time the board is on the bench, before the dev's first upload if possible.

## What the dev must stay inside
1. **Call `fast_peripherals()` before creating the `SPI` object.** MicroPython computes the SPI divider from the clock it believes `clk_peri` has, and it caches that at boot. The fix does not update the cache, so:
2. **Every baud you request is really 2.6x (125/48) what MicroPython thinks.** Requesting `62_500_000` prints `baudrate=24000000` and runs at a real 62.5 MHz, which is what you want. But the DR's fallback, "request 31.25 MHz instead", **will not work**: MicroPython picks the highest nominal rate at or below the request from {24, 12, 6, …} MHz, so 31.25 MHz → nominal 24 MHz → real 62.5 MHz, unchanged. To really get 31.25 MHz with the fix on, request **12_000_000** (nominal 12 → real 31.25). Put this table in a comment next to the `SPI(...)` line.
3. **Verify by timing, never by the repr.** `utime.ticks_us()` around one `show()`: about 17–19 ms means the fix is on, about 46 ms means it is off.
4. Keep the off switch (`FAST_SPI`). If the picture ever looks wrong at full speed, the test is: switch off → 46 ms frames and a clean picture means the panel or wiring dislikes 62.5 MHz, and the answer is request `12_000_000` with the fix on.
5. Nothing else on `clk_peri`. UART0/1 would run at the wrong baud after the fix; this project has no UART, and the USB REPL that Viper uses is on its own clock (confirmed: the REPL kept working through every fix run).
6. Soft reset keeps the fast state, power cycle clears it; the idempotency check makes both paths end the same way. Confirmed on the board both ways (2026-10-03 soft reset left `0x800`; 2026-10-04 power cycle gave `0x840`).
