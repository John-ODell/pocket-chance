# HR-008: Review of DR-008, missing or corrupt save file

- **Verdict: fits**
- Reviewer: microcontroller expert, 2026-10-03. Numbers from `hwtest/flash_write.py`, `hwtest/flash_read.py`.

## Numbers
- Keeping `/save.bak` means one extra rename (or copy) per save. A rename is a few ms; the whole save sequence (write tmp, rename old → bak, rename tmp → json) stays around **25–30 ms typical, ~100 ms worst case**, once per round. Fine between hands.
- Reading and checking three 40-byte files at boot costs under 5 ms total. Nothing the player will notice.
- Flash: three 40-byte files occupy three 4 KB blocks at most (LittleFS inlines small files, so usually less). Irrelevant against 1.39 MB free.

## What the dev must stay inside
1. Order of operations on save, so there is always one valid file on disk: write `save.tmp`, `rename(save.json → save.bak)`, `rename(save.tmp → save.json)`. If power fails between the two renames, `save.json` is missing but `save.bak` is the last good save, which the loader already handles.
2. Wrap every file operation at boot in `try/except OSError`; a missing file is `ENOENT`, not a crash. The loader must never raise, as the dev says.
3. The on-screen message needs the display initialised first. Load the save **after** the LCD is up, so a damaged file can be reported, and keep the message path free of any further file access.

## Nothing outstanding
No measurement gap for this request.
