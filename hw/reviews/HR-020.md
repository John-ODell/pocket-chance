# HR-020: Review of DR-020, slots spin animation

- **Verdict: does not fit as described; fits with limits with the draw path changed as below.** Option A's idea (scroll the real strip inside each window, compose in scratch, push three windows) is right. Two details in its description cost 4x the budget and both are easy to change.
- Reviewer: microcontroller expert, 2026-10-04. Scripts `hwtest/slots_spin_bench.py` (as described) and `hwtest/slots_spin_bench2.py` (fixed path), real `lib/lcd.py`, `lib/art.py`, `framebuf`, SPI at 62.5 MHz and at 24 MHz, stand-in 56x56 symbol files on flash, three windows at x = 18/92/166.

## Measured

| Three reels moving, 8 px/frame | 62.5 MHz | 24 MHz (as shipped) |
|---|---|---|
| **As described**: two `Assets.blit` reads from flash per reel per frame, compose copied into the framebuffer, `show_rect` | **82 ms, 12 fps** (max 97) | 90 ms, 11 fps |
| As described but compose pushed directly to the panel (no copy, no `show_rect`) | 57 ms, 18 fps | 61 ms |
| **Fixed path**: symbols held in RAM, read only when one scrolls in; compose pushed directly | **13.1 ms, 76 fps** (max 14.3) | **17.7 ms, 56 fps** (max 28) |
| Fixed path, the frame where symbols change (6 flash reads, two RAM slots shared by all reels) | 38 ms | 42 ms |
| One reel moving (end of spin), fixed path | 4.5 ms | |

Where the time goes, per reel, as described: two reads and blits **16.4 ms**, compose → framebuffer copy 2.9 ms, `show_rect` 7.1 ms (its Python row loop), of which the actual push is 1.5 ms.

The parts behind that: `os.stat` on this filesystem **3.7 ms**; open + read of one 6,276-byte symbol 4.1 ms; two keyed blits from RAM into the compose 2.9 ms; one unkeyed blit 1.6 ms; direct push of a 56x56 window 1.5 ms.

RAM: the fixed path with two shared symbol slots plus the compose buffer is 19.1 KB; free after it 82.9 KB (slots module not yet loaded, estimate ~5 KB).

## Why the estimate missed
1. `Assets.blit` is not a 1.5 ms read. It calls `os.stat` (3.7 ms) and `open` and reads the header before the pixels, about **8 ms per sprite** on this LittleFS, every call. Blackjack never noticed because it blits a few cards per key press, not six per frame. Filed separately as HR-F03, because fixing it in `art.py` helps every game.
2. "Copy the compose into the framebuffer then `show_rect`" costs 10 ms per reel. The compose buffer already holds exactly the window's pixels: set the window and write it to the panel. The main framebuffer need not be touched during the spin; redraw the windows into it once when the reels stop.

## Limits for the dev (the "fits" depends on all of them)
1. **Symbols in RAM during a spin.** Read a symbol from flash only when it scrolls into a window, never per frame. Minimum: two 6,272-byte slots (current, next) per reel, 37.6 KB for three reels, plus the 6,272-byte compose; or two slots shared by all reels (19 KB) and accept a 38 ms frame once every seven frames (a visible judder at 8 px/frame).
2. **Stagger the reels** so their symbol changes fall on different frames; then at most one reel reads per frame and the worst frame is about 17 ms (13 + one 4 ms read).
3. **Push the compose directly** (`_window` + `_push`, or a small `LCD.show_buf(x, y, w, h, buf)` added to the driver) instead of blit-to-framebuffer + `show_rect`.
4. No `os.stat`, `open`, `FrameBuffer()` construction or any allocation inside the frame loop. Build the compose and slot `FrameBuffer`s once.
5. Design floor stays 20 fps as the dev says; the fixed path gives 56–76 fps, so 8 px/frame at ~50 fps is a smooth spin and there is room for the slow-down.
6. With limits 1–4, option A at 24 MHz is 17.7 ms per frame, so the animation is fine even if the clock fix is ever off.

## Recommendation
Option A with limits 1–4. Keep `sym_blur` dropped. The fallback the dev offers (4 px steps) is not needed.

## Revision 2 RAM choice, measured 2026-10-04 (`hwtest/slots_ram_bench.py`)
The 82.9 KB figure in the table above was taken with no menu loaded. With the real `pocket.py` menu set up and a game module imported the way `play()` does (blackjack as the stand-in; the slots screen will be the same size class), the board has:

| State | Free | Largest block |
|---|---|---|
| Menu ready, no game module | 75,408 | 48,488 |
| Game module imported (cost 14,288) | **69,648** | 43,354 |
| **Option A: 6 slots + compose (43,904 B)** | **does not fit**: fails on the 6th buffer | |
| **Option B: 2 shared slots + compose (18,816 B)** | fits, **50,656 left**, largest block 24,497 | |
| Middle: 3 slots + compose (25,088 B) | fits, 44,368 left, largest block 18,165 | |

**Use fallback B.** Option A is out: even if it squeezed in on a fresh boot it would leave single-digit KB and fail after fragmentation. B's cost is the 38 ms frame when a reel's symbols change (the six reads); limit 2 (stagger the reels) cuts that to one reel's reads per frame, so with B the worst frame is about 13 + 8 = 21 ms and the steady frame 13 ms. Still 48+ fps, still fits. The 3-slot middle buys nothing B plus staggering does not already give.

Also measured with step 1f in place: `Assets.load` 3.9 ms per symbol (what the wrap frame pays per read), `LCD.show_buf` 56x56 1.9 ms (the direct push, limit 3).

## As built (step 1g, measured 2026-10-04)
The dev built the fixed path with fallback B as three per-reel window buffers scrolled with `FrameBuffer.scroll` and rows read from the incoming symbol's open file (`hwtest/slots_play_bench.py`, real code, stand-in symbols):

| | Measured | Dev expected |
|---|---|---|
| Steady frame | **10.8 ms** mean, 17.8 max | 8–10 ms |
| Symbol-change frame | 14.9 ms mean, 19.9 max | ~13 ms |
| Overruns of the 20 ms pace | 0 in 260 frames | |
| **Free RAM mid-spin, real program** (`pocket_scripted.py`) | **36,432** | 45–50 KB; alarm under 20 KB |
| Save after spin / blink / paytable | 63 ms (110 max) / 784 ms / 111 ms | |

Verdict stands: **fits**. The one incident: `UPLOAD.md` step 1g omitted the `lib/art.py` that provides `open_sprite`, so the four listed files crash on the first spin; caught on the bench, the dev's committed `art.py` uploaded, the step needs the fifth row. With DR-024's symbol sheet the per-change file open (3.7 ms) goes away and the change frame falls to the steady frame.

## Not measured
The slow-down and snap phases (fewer pixels per frame, same cost per frame). Real symbol art instead of striped stand-ins (same byte count, same cost).
