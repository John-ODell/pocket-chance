## 1. Appendix A: does today's software carry to an RP2350A?

### Pin map: yes
The RP2350A exposes GPIO 0–29 with the same numbering and the same peripheral mapping for the pins we use (SPI1 SCK on GP10, TX on GP11; the rest are plain GPIO with pull-ups). Source: Raspberry Pi's chip comparison and the RP2350 datasheet pin tables (not re-read by me; the PCB maker's reading stands). `lib/lcd.py`, `lib/buttons.py` and `games/` need no pin changes. Verified only by documentation; confirm the SPI1 function assignment for GP10/11 in the datasheet's GPIO function table before freezing the schematic.

### `lib/clocks.py`: the problem carries over, the fix should not
What I found in the sources today:
- pico-sdk, `src/rp2_common/hardware_clocks/clocks.c`, `set_sys_clock_pll()`: by default it runs `clock_configure_undivided(clk_peri, 0, CLOCKS_CLK_PERI_CTRL_AUXSRC_VALUE_CLKSRC_PLL_USB, USB_CLK_HZ)`, i.e. **clk_peri on the 48 MHz USB PLL**. Only when the build defines `PICO_CLOCK_ADJUST_PERI_CLOCK_WITH_SYS_CLOCK` does it use `CLKSRC_PLL_SYS` at the system frequency. This code is in `rp2_common`, shared by RP2040 and RP2350; I saw no chip-specific `#if` around it.
- MicroPython, `ports/rp2/main.c`: calls `set_sys_clock_khz(SYS_CLK_KHZ, false)` with the comment "as a side effect the peripheral clock to 48 MHz", in common code with no chip or board condition.

So the 24 MHz SPI cap we measured on the Waveshare v1.29.0 build is the SDK's default for **every** rp2 MicroPython board that does not set that flag, including the `RPI_PICO2` and `RPI_PICO2_W` builds unless their board files set it (not checked; treat as "same cap" until measured). This answers the PCB maker's first question without a Pico 2: **expect SPI(1) at 62.5 MHz requested to be granted 24 MHz on a stock Pico 2 build**, and the register poke to be needed again.

Limits for the port:
1. **Do not port `lib/clocks.py` by changing the address.** The RP2040 constants in it (`0x40008048`, the AUXSRC field layout) are RP2040-specific; the RP2350 clock block lives at a different base (the PCB maker reads `CLOCKS_BASE = 0x40010000`, so `CLK_PERI_CTRL` at `0x40010048`, from the RP2350 datasheet; that matches my recollection but I could not fetch the SDK header today, so **confirm it in the datasheet's address map before anyone pokes it**) and the field encodings may differ. A wrong poke on a clock register can stop the UART, the SPI or the chip.
2. **The clean fix for a custom board is firmware, not a poke:** a custom MicroPython board definition (we need one anyway for the PSRAM CS pin and the 16 MB flash) that sets `PICO_CLOCK_ADJUST_PERI_CLOCK_WITH_SYS_CLOCK=1`. Then `clk_peri` follows the system clock, `SPI(1, 62_500_000)` is honest again, and `lib/clocks.py` is deleted, with `FAST_SPI` becoming a no-op. The dev's `is_fast()` check should turn into "measure one `show()` with `ticks_us` and print it at boot" so a wrong build is noticed.
3. **System clock and SPI divider.** The RP2350 runs 150 MHz by default; `clk_peri = clk_sys` gives SPI at 75 MHz for /2 and 37.5 MHz for /4. The panel is verified at 62.5 MHz, not 75. Either run the system clock at 125 MHz (`machine.freq(125_000_000)`, same timings as today) or request a divider that lands at or below 62.5 MHz and re-check the panel by eye, as we did on 2026-10-04. Do not assume 75 MHz is clean.
4. **Re-measure everything** on the first board: `hwtest/` scripts run unchanged on an RP2350 MicroPython; `BUDGET.md` gets a second column.

### PSRAM: agree with the caveat, and add one
MicroPython places the heap across SRAM and PSRAM without per-object control. The 115 KB framebuffer must stay in fast SRAM, or every `show()` reads it over the QSPI PSRAM at a fraction of SRAM speed. Check at bring-up: allocate the framebuffer first thing after boot (today's HR-001 rule already does this), then time `show()`; if it is not ~17 ms at the same SPI speed, the buffer landed in PSRAM and the port needs the SRAM-first heap option. Unverified; it is the first measurement I would run on the new board.

## 2. Appendix D: the battery and power chain (second opinion, role rule 7)

| Block | Opinion |
|---|---|
| **Charger** | MCP73831, agreed: linear, 500 mA max, SOT-23-5, one resistor, the hobby standard with years of reference designs. Set the current to ≤ 0.5 C of the cell (500 mA for 1000 mAh). It gets warm at 500 mA from 5 V into a low cell (about 1 W dissipated); give it copper. The ETA6096 is cheaper but its documentation is thinner; for a first board take the part with the most published designs. **Charge only from USB 5 V; never charge while the board is also drawing hard from the cell without checking the charger's thermal regulation (the MCP73831 has it).** |
| **Protection** | DW01A + FS8205A, agreed, plus a protected cell: belt and braces. Note the DW01A's over-discharge cut-off is about 2.4–2.5 V, which is below where a 3.3 V regulator is useful; the software low-battery warning (via the gauge or an ADC divider) should act well before that, around 3.4–3.5 V. |
| **Regulator** | **Buck-boost, not an LDO.** A LiPo spends most of its life between 3.9 and 3.5 V. A 3.3 V LDO with ~0.2 V dropout browns out at ~3.5 V, so you lose the bottom third of the cell and the board resets mid-game as the backlight pulls the rail down. The Plus's MP28164 (2 A buck-boost) is proven in this exact role; a TPS63001-class part is the other common choice. Two cautions: (a) switching regulators put ripple on the rail, so place the ADC reference and the ST7789's supply decoupling away from it and follow the datasheet layout; (b) **size it from a measurement, not a guess**: `hwtest/load_hold.py` holds the board at full backlight and full-frame pushes for John's multimeter session, and an inline current reading at the same time gives the number that picks the part. My estimate until then: RP2040 at 125 MHz ~35–45 mA, 1.3" panel plus backlight at 100 % ~40–60 mA, total **~100 mA, under 150 mA**; the RP2350 at 150 MHz with PSRAM will add some tens of mA. Any 500 mA-class buck-boost is plenty; the measurement is to confirm, not to size up. |
| **Power switch on the regulator enable** | Agreed and standard: small switch, no high current through it, charging works with the switch off. Add a pull-down on the enable so the board is off with no switch fitted, and check the chosen regulator's enable logic level against the cell voltage range. |
| **Fuel gauge** | MAX17048 on I2C is the nicer answer; the ADC divider (two resistors into a free ADC, GP26–28) is the one I would put on spin 1 because it cannot fail and costs nothing; add the gauge footprint. Keep the divider's current tiny (≥ 100 kΩ total) or switch it with a GPIO, or it drains the cell on the shelf. |
| **Speaker** | PAM8302A with PWM audio through an RC filter is the least software risk (`machine.PWM` exists, works today for the backlight). I2S is cleaner but it is new code on this port for us. Footprint only on spin 1, as proposed. Mind that PWM audio at ~22 kHz carrier can couple into the ADC divider reading; sample the battery when audio is idle. |
| **First power-up** | Agreed: current-limited supply, no cell fitted, then cell with the USB disconnected, then both. I will write the bring-up checklist as `hwtest/` scripts when the board exists. |

**What I could not verify:** none of the part datasheets were read by me today; the opinions above are from the parts' general reputation and the Plus's own choices. Read each datasheet's reference schematic before placing.

## 3. Appendix B: RM2 pins for the stock `RPI_PICO2_W` build
Read from pico-sdk `src/boards/include/boards/pico2_w.h` today (verbatim defines): `CYW43_DEFAULT_PIN_WL_REG_ON 23u`, `CYW43_DEFAULT_PIN_WL_DATA_OUT 24u`, `CYW43_DEFAULT_PIN_WL_DATA_IN 24u`, `CYW43_DEFAULT_PIN_WL_HOST_WAKE 24u`, `CYW43_DEFAULT_PIN_WL_CLOCK 29u`, `CYW43_DEFAULT_PIN_WL_CS 25u`; also `PICO_VSYS_PIN 29` and `CYW43_WL_GPIO_LED_PIN 0` (the LED hangs off the radio chip's GPIO0, not an RP2350 pin), `CYW43_WL_GPIO_SMPS_PIN 1`, `CYW43_WL_GPIO_VBUS_PIN 2`.

So the stock build expects: **REG_ON on GP23, the single bidirectional data line on GP24, CS on GP25, CLK on GP29**, and it reads VSYS through GP29 as well (the Pico 2 W shares GP29 between the radio clock and the VSYS divider, with care in the firmware). The DR's claim "GP23, GP24, GP25, GP29" is **correct**, and those are exactly the pins the game never uses (`hw/BOARD.md`: 23 and 25 float, 24 is the VBUS sense, 29 unconnected on the Plus). Limits: (1) route the RM2's gSPI lines to those four pins so spin 1 can run the stock `RPI_PICO2_W` build with the module populated, even if a custom board definition comes later; (2) the stock build's flash size define is 4 MB (`PICO_FLASH_SIZE_BYTES (4 * 1024 * 1024)`), so with a 16 MB chip we need our own board definition anyway, which is also where the `clk_peri` flag and the PSRAM CS pin go; (3) if GP29 is also wanted for VSYS sensing, copy the Pico 2 W's arrangement exactly or move the battery divider to GP26–28 and leave GP29 to the radio. Which RM2 castellation is which signal I did not read; take it from the RM2 datasheet.
